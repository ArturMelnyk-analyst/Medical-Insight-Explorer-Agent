# LLM Response Layer

## Purpose

The response layer converts deterministic healthcare analytics results into grounded, human-readable explanations.

The project follows a computation-first principle:

```text
Compute first.
Explain second.
```

Healthcare statistics are produced by deterministic pandas analytics rather than generated by an LLM.

Optional LLM support is limited to explanation and does not provide direct access to healthcare dataframes or unrestricted analytical execution.

---

## Design Principle

The response architecture separates calculation from interpretation:

```text
User question
        ↓
Approved analytical capability
        ↓
Deterministic pandas calculation
        ↓
Computed result
        ↓
Analytical insight
        ↓
Response formatting
        ↓
Optional LLM explanation support
```

This keeps numerical outputs grounded in predefined analytics functions.

---

## Components

| Component | Purpose |
|---|---|
| `QueryRouter` | Maps supported single-step questions to analytical routes |
| `ResponseGenerator` | Provides the standalone controlled response path |
| `response_formatter.py` | Formats deterministic analytical results for presentation |
| `insight_layer.py` | Produces cautious analytical interpretation from computed results |
| `prompt_templates.py` | Stores prompts used by optional LLM explanation support |
| `tool_registry.py` | Defines the approved deterministic analytics capabilities available for execution |

---

## Two Execution Paths

The project intentionally retains two execution paths.

### Standalone Response Path

`ResponseGenerator` provides the standalone controlled response workflow:

```text
Question
   ↓
QueryRouter
   ↓
Approved tool registry
   ↓
Deterministic analytics
   ↓
Response generation
   ↓
Optional LLM explanation
```

This path preserves the original single-step response architecture.

### LangGraph Application Path

The deployed application uses `HealthcareGraphWorkflow` for controlled orchestration:

```text
Question
   ↓
Language normalization
   ↓
Bounded analytics planning
   ↓
Approved tool registry
   ↓
Deterministic analytics
   ↓
Analytical insight
   ↓
Response formatting
```

Supported compound questions can execute multiple approved analytical tools and synthesize their results into one response.

Detailed planner behavior is documented in [LangGraph Orchestration](langgraph_orchestration.md).

---

## Approved Analytics Boundary

Both execution paths use the shared approved analytics tool registry.

The registry acts as the controlled boundary between routing or planning and deterministic computation:

```text
routing / planning
        ↓
approved tool name
        ↓
tool registry
        ↓
HealthcareAnalyticsEngine
```

The response layer does not permit arbitrary analytics-engine method selection or unrestricted dataframe operations.

For the complete capability model, see [Architecture](architecture.md).

---

## Analytical Insight Layer

The analytical insight layer interprets already-computed results using cautious, descriptive language.

It can highlight patterns such as:

- relative differences
- distributions
- provider activity
- geographic variation
- reimbursement patterns

It does not create new healthcare statistics or convert associations into causal conclusions.

For multi-step workflows, insights can summarize relationships across the deterministic results returned by the executed analytical tools.

---

## Multi-Result Responses

Version v1.2.0 supports response synthesis for selected multi-step analytical workflows.

A multi-step response can include:

- summary
- analytical workflow
- analytical steps
- analytical insight
- computed results from each executed tool
- method note
- safety note

Only analytical operations that were actually executed are presented.

The response does not expose private chain-of-thought or hidden reasoning.

---

## Optional LLM Support

The response architecture can operate without an LLM.

When optional LLM explanation support is disabled, responses remain grounded in deterministic analytical results and predefined response logic.

When enabled, the LLM is used to explain already-computed results rather than calculate healthcare statistics directly.

Conceptually:

```text
Deterministic analytics
        ↓
verified computed result
        ↓
optional LLM explanation
```

The LLM does not receive unrestricted dataframe access and does not replace the deterministic analytics engine.

The deployed application should therefore not be interpreted as depending on an LLM for numerical healthcare calculations.

---

## Fallback Behavior

Unsupported requests are handled through controlled fallback behavior rather than arbitrary analytical execution.

Causal medical requests are also outside the supported analytical scope.

These requests do not cause the system to generate new Python, SQL, pandas operations, or arbitrary analytics-engine calls.

---

## Safety Boundaries

The response layer does not:

- diagnose patients
- recommend treatment
- make clinical decisions
- determine fraud
- invent unsupported healthcare statistics
- make causal medical conclusions
- execute arbitrary Python, SQL, or pandas operations

For complete project boundaries, see [Limitations](limitations.md).

---

## Summary

The response architecture follows a deterministic-first pattern:

```text
approved analytics
        ↓
deterministic result
        ↓
analytical interpretation
        ↓
human-readable response
        ↓
optional LLM explanation
```

The LLM, when enabled, supports explanation rather than computation.

This preserves a clear boundary between healthcare claims analytics and natural-language presentation.
