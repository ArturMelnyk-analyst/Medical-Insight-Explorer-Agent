# Data Contract — Medical Insight Explorer Agent

## Purpose

This document defines the cleaned Parquet inputs expected by **Medical Insight Explorer Agent**.

The project consumes validated outputs generated by the upstream `Healthcare-Data-Cleaning` repository rather than processing the original raw CSV files directly.

---

## Expected Data Locations

Full processed Parquet files are stored locally under:

```text
data/processed/
```

These files are intentionally excluded from GitHub.

The lightweight public deployment can use sample Parquet files under:

```text
data/sample/
```

For deployment behavior, see [Deployment Guide](deployment.md).

---

## Required Parquet Tables

| Logical Table | Expected File | Role |
|---|---|---|
| `train_beneficiary` | `train_beneficiary_clean.parquet` | Cleaned training beneficiary table |
| `test_beneficiary` | `test_beneficiary_clean.parquet` | Cleaned test beneficiary table |
| `train_inpatient` | `train_inpatient_clean.parquet` | Cleaned training inpatient claims table |
| `test_inpatient` | `test_inpatient_clean.parquet` | Cleaned test inpatient claims table |
| `train_outpatient` | `train_outpatient_clean.parquet` | Cleaned training outpatient claims table |
| `test_outpatient` | `test_outpatient_clean.parquet` | Cleaned test outpatient claims table |
| `train_labels` | `train_labels_clean.parquet` | Training provider-level label table |
| `test_labels` | `test_labels_clean.parquet` | Test provider-level label table |

---

## Key Relationship Fields

| Field | Purpose |
|---|---|
| `BeneID` | Connects beneficiary records to inpatient and outpatient claims |
| `ClaimID` | Identifies individual claim records |
| `Provider` | Connects claim records to provider-level label tables |

These identifiers support the relational structure used by the downstream analytics layer.

---

## Data Flow

The expected data flow is:

```text
Raw healthcare data
        ↓
Healthcare-Data-Cleaning
        ↓
cleaned and validated Parquet files
        ↓
data/processed/
        ↓
HealthcareDataLoader
        ↓
HealthcareAnalyticsEngine
        ↓
controlled analytics workflow
```

The Medical Insight Explorer Agent therefore treats cleaned Parquet files as its analytical input boundary.

---

## Data Loading

`HealthcareDataLoader` is responsible for loading the expected Parquet tables into the application.

The downstream analytics engine operates on these loaded and cleaned datasets rather than performing the upstream data-cleaning process again.

This separation keeps:

```text
data preparation
```

and:

```text
analytics + orchestration
```

as distinct project responsibilities.

---

## Data Governance

Full processed healthcare datasets are not committed to the GitHub repository.

The local workflow is:

1. Generate cleaned Parquet files using `Healthcare-Data-Cleaning`.
2. Place the required files under `data/processed/`.
3. Load them through `HealthcareDataLoader`.
4. Run deterministic analytics on the validated inputs.

The public Hugging Face deployment uses lightweight sample data instead of the complete processed dataset.

Sample-data results may therefore differ from full local results.

---

## Contract Boundary

This project assumes that the upstream cleaning pipeline has already prepared and validated the required Parquet inputs.

The data contract defines:

- expected tables
- expected filenames
- storage locations
- key relational identifiers
- the boundary between upstream cleaning and downstream analytics

It does not redefine the upstream cleaning methodology or the downstream analytics calculations.

For those responsibilities, see:

- [Analytics Engine](analytics_engine.md)
- [Architecture](architecture.md)
- [Deployment Guide](deployment.md)

---

## Summary

The data boundary is intentionally simple:

```text
Healthcare-Data-Cleaning
        ↓
validated Parquet files
        ↓
Medical Insight Explorer Agent
```

This keeps data preparation separate from deterministic analytics, orchestration, visualization, and user-facing interpretation.
